Day 15 — Describe the experiment without overstating it

Lecture slides · Weekly self-check

Today’s question

Can a reader understand the seedling measurements, their variation, and the limits of our description? A useful biological report does not need a significance test on every page. Today you will make the data handling, figure, summary, and interpretation fit together.

Save a new source document, descriptive-report.Rmd, at the project root. You may copy your first report’s structure, but deliberately revise its methods and interpretation. Keep data/ paths relative to this root. The supplied measurements are simulated. Plants received a control or nutrient treatment and were measured seven days apart; the nutrient formulation is unspecified.

Produce one descriptive report today. The teacher may choose the organic laboratory alternative below instead of the seedling report. In that case save organic-report.Rmd at the same project root and use its stated variables and units throughout; do not mix the two datasets in one set of results.

Choose and state which input you use

Use data/seedlings.csv for the core report. It contains 24 complete plant records. Include a data-quality note explaining the checks you performed: unique plant IDs, allowed treatment labels, numeric length columns, and missing-value counts. A statement that “R loaded the file” is not a data-quality check.

If the teacher asks you to report the repaired day 11 data instead, include the repair code or source it from a saved script within the project. Do not read a derived file that cannot be recreated from the shared raw data. State which source you used and retain the unavailable P06 observation; do not silently mix results from the repaired and complete datasets.

Build the report in a clear order

Use this order inside the report:

  1. Load packages and import the input file.
  2. Inspect its structure and document relevant data checks.
  3. Derive growth_mm = final_mm - initial_mm.
  4. Calculate the grouped summary with sample counts, mean, median, and SD.
  5. Draw the individual-plant figure with group means.
  6. Explain the centre, spread, overlap, and limitations in ordinary language.

Here is a compact data-check block that can appear after import:

library(readr)
library(dplyr)
seedlings <- read_csv("data/seedlings.csv", show_col_types = FALSE)
anyDuplicated(seedlings$plant_id)
seedlings |> count(treatment)
sum(is.na(seedlings$initial_mm))
sum(is.na(seedlings$final_mm))
seedlings <- mutate(seedlings, growth_mm = final_mm - initial_mm)

anyDuplicated() returns zero when it finds no duplicate; a positive result identifies the position of the first duplicate, not a count of duplicates. Include only checking output that helps the reader, but keep the code available in the source. Reuse your day 13 summary and figure rather than replacing them with a screenshot of the RStudio Environment pane.

A table in an R Markdown chunk can be displayed neatly with:

group_summary <- seedlings |>
  group_by(treatment) |>
  summarise(n_observed = sum(!is.na(growth_mm)),
            mean_mm = mean(growth_mm, na.rm = TRUE),
            median_mm = median(growth_mm, na.rm = TRUE),
            sd_mm = sd(growth_mm, na.rm = TRUE), .groups = "drop")
knitr::kable(group_summary, digits = 2,
             caption = "Observed growth and variation by treatment; lengths in mm.")

The table is generated from code. If the data change, the rendered table can change too. A caption must distinguish SD among plants from uncertainty in the mean. This report has SD, not confidence intervals.

Write with the question in view

A useful description distinguishes three ideas: group averages differ in this sample; plants vary within each group; and sample descriptions do not quantify all uncertainty about a treatment effect. You can report observed values with units and identify the independent unit without declaring a universal result.

For the complete data, the group means are about 15.3 mm for controls and 21.5 mm for treated plants. Check your table rather than copying these numbers into prose without verification. The treated group also has more spread in these data. Do not say that every treated plant outgrew every control plant: the individual observations overlap.

Alternative context: report collected-product yield

Use this in place of the seedling report if selected. The question is: what percentage of the supplied maximum product mass was collected in each run, and how does it vary between protocols? All data are simulated. A synthesis run is one independently carried-out product-making experiment. Twelve independent runs were randomly assigned to two protocols, six to each. A protocol is a specified method; no knowledge of its chemical steps is required here.

theoretical_mass_g is the supplied maximum possible product mass for that run’s starting amounts. isolated_mass_g is the dry collected product mass, assumed pure for this simplified calculation. Both are in grams. Calculate percentage yield with 100 * isolated_mass_g / theoretical_mass_g, so Y01 is 100 * 0.62 / 1.00 = 62%. Theoretical masses differ with starting scale; compare the percentages, not the raw masses. You do not need to balance a reaction or calculate a theoretical mass yourself.

organic <- read_csv("data/organic-recovery.csv", show_col_types = FALSE) |>
  mutate(yield_percent = 100 * isolated_mass_g / theoretical_mass_g)
organic_summary <- organic |>
  group_by(protocol) |>
  summarise(n_runs = n(), mean_yield_percent = mean(yield_percent),
            sd_percentage_points = sd(yield_percent), .groups = "drop")
organic_summary

Follow the same report order: import and check IDs, labels, numeric masses, missing values, and positive theoretical masses; calculate yield; show a table and individual-run plot; then interpret centre, spread, and overlap. Both groups have six available runs. Mean yields are about 68.67% and 77.00%; SDs are about 4.32 and 3.74 percentage points for standard and modified protocols. Label the y-axis “Isolated product yield (%)” and identify one point as one run. Do not call repeated weighings of one product batch independent runs.

This is descriptive work: no t-test is needed. A higher mean yield does not establish greater purity, safety, environmental benefit, or superiority in other reactions. Write a limitation tied to the small simulated set and the assumed purity. Keep the source and data together so the report can render from scratch.

Your practical and a reader check

  1. Complete the report with a question, data/design paragraph, methods, table, figure, and interpretation. Keep it short enough that each part earns its place.
  2. Include the number of independent plants, or independent synthesis runs for the alternative, and state what the figure’s symbols represent. Name any exclusions or missing measurements.
  3. Restart R and run this command in the R Console, not in a code chunk inside the report (a report must not try to render itself):
rmarkdown::render("descriptive-report.Rmd", output_dir = "reports")

For the organic alternative, replace the quoted filename with "organic-report.Rmd"; render only the report you chose.

  1. Ask a partner to read the HTML. Can they identify the units, input file, observational unit, main pattern, and main limitation without opening RStudio?
  2. If remote R access is available, locate the project on that computer and repeat the render there using the supplied connection instructions. First identify whether the R session and data are local or remote. Otherwise, repeat from a newly opened local project; do not invent connection details.
Hint: reproducibility is a file relationship

An HTML file beside an .Rmd is not enough if the source expects data in your personal Downloads folder. Keep the documented project structure, original data, and source together. The fresh-session render reveals missing dependencies.

Check your understanding

A good limitation is specific

“The sample is small” is less informative than naming the independent unit, noting overlap or variation, and explaining that today’s report describes the sample without yet estimating uncertainty in a treatment difference. Missing observations, when present, should also be counted and discussed.

Extended practical — edit a report as a reader, then as an analyst

Plan 75–90 minutes of revision of the one descriptive report you selected. Do not create a second compulsory biology/chemistry report just to make the session longer. The goal is a complete short scientific account with a traceable analysis, not more headings or a longer printout. Save a revision log in reports/day15-revision.txt alongside your own report source at project root.

  1. Read only the rendered HTML, with the code initially closed. Write down the question, independent unit, input filename, measurement or derived outcome, and units. If any cannot be found, add a specific sentence or label rather than relying on the reader to infer it from an object name.
  2. Inspect every numerical statement. Match it to the code and table that produced it. Check n against available observations, not all lines in a CSV. Record whether you used complete seedling data, the repaired exercise, or the independent organic-run context, and carry that choice through all counts, captions, and limitations.
  3. Replace three weak sentences. Use these starting examples: “The results were good”; “the treatment had more error”; “the computer removed the bad values.” Your replacements must identify a measured pattern, a defined quantity such as SD, or an evidence-supported action. Avoid claiming an effect has been tested in this descriptive report.
  4. Check that the figure shows observations with units. Identify what each summary symbol means. Put the figure beside a small table that answers a complementary question; remove redundant raw printouts if they do not help a reader. More pages are not automatically more reproducible.
  5. Add two inline values in the results prose using the R Markdown pattern already introduced: one count and one mean or SD. Test them by rendering. The object must be created earlier inside the document. Keep interpretation in ordinary prose rather than assuming inline code writes a conclusion.
  6. Ask a partner to reproduce the report from a complete project copy. If working alone, extract a fresh course folder in a new temporary location, add your source and required inputs, and render there. Record the first failure before fixing it. A relative input path is useful only if the needed data file was actually included.
  7. Save the revised HTML and its .Rmd source. Write a compact change log: issue, evidence, correction, and rerun result. Keep the previous source as a clearly named backup or ordinary copied file, without inventing a complicated version-control workflow.
Hint: separate numerical checks from wording checks

The complete seedling table has 24 plants; the repaired exercise has 24 plant records but 23 observed growths. The organic alternative has 12 independent runs, six per protocol, with no missing masses. A report may use any selected route, but cannot switch silently between these denominators. Use the Console for a rmarkdown::render() call; never put a self-render command into the report.

Independent transfer — a new class asks for a concise descriptive report

Allow 60–90 minutes, extending to another session if rendering needs support. The new class supplies data/seedlings-transfer.csv: 18 independent potted plants, nine randomly assigned to each allocation, initial and final lengths in mm seven days apart. The task is to describe growth and its variation; it is not yet a request for a significance test.

  1. Create transfer-description.Rmd in the project root. Start from your chosen source’s structure, but remove old imports, variable names, numbers, and biological descriptions that no longer apply. A template is a structure to adapt, not evidence that the old findings describe new observations.
  2. State the new question, independent unit, input, units, and growth formula. Include checks for identifiers, group counts, and missingness in the saved source. If you used the transfer dataset in earlier scripts, recreate its objects inside this report rather than depending on the Environment pane.
  3. Produce one labelled individual-point figure and a group table with n, mean, median, and SD. Choose sensible rounding in the displayed table. Explain the distinction between the 18 input rows and the two summary rows.
  4. Write 150–250 words of results and interpretation, using calculated numbers and one limitation. Address direction, overlap, and spread. Do not translate a higher mean into “every treated plant did better”, or SD into uncertainty in a difference. Independent comparison methods arrive in the next block.
  5. Render after restarting and locate the actual output HTML. If you render into reports/, document that destination. Confirm that changing only the report title does not change its calculations, and that changing an input filename requires appropriate new checks and prose.
  6. Make a one-page handover note listing the minimum files needed to reproduce the new report. Open the report on another computer if supported; otherwise use a separately located project copy. Record which kind of portability check you actually performed, without claiming an untested environment.

Additional outputs: revised chosen report, revision log, the self-contained transfer report and HTML, and the handover note. You should now be able to explain both what the observations show and how a reader can regenerate them.

Keep: your chosen descriptive-report.Rmd or organic-report.Rmd and its HTML, with the code and data needed to render it. Next: from description to a comparison.
